| 2026-08-20 | Design | Decorative highlight/glow overlays must be FULL-BLEED (`inset-0`) and fade to zero alpha inside their own box. A partial-size box with a linear gradient fades on one axis only, so its other edges cut off hard and render as visible rectangles — that was Panel `specularMode="halo"`. | 2026-08-20 | Tailwind | A helper that returns class strings must return ONE concern. `getSpecularClasses` returned paint *and* layout while every caller also applied its own layout, so `inset-0` fought `inset-x-0 top-0 h-[10px]` and emission order silently decided the winner. | 2026-08-20 | Design | Contrast on glass is a function of fill opacity, not text colour — CSS cannot see the backdrop. A `{color}-900` label needs ~85 % fill to stay legible over a dark photo; at 55 % it fails. Ship sheer presets, but document which one is safe over busy backdrops rather than trying to auto-correct. | glass.ts |

| 2026-08-20 | Design | A sweeping highlight needs shape, not just travel. A full-height rectangle sliding across reads as "a box moving" no matter how you tune the gradient. | 2026-08-20 | Design | An effect nobody can see reads as a broken toggle. `GlassBackground`'s shimmer (`white/0.08`, mostly off-container) and ambient glows (unsafelisted colour, 0.12 opacity) both technically rendered, so the demo toggles "did nothing". | 2026-08-20 | Tailwind | You cannot simulate a `:hover` state by passing the hover classes as a plain `className` — both rules target the same property at the same specificity, so the stylesheet's own order decides, not the class attribute. `.hover\:x:hover` wins over `.x` by specificity, which is why real hover works while the simulation showed no change. | 2026-08-20 | Design | An opacity step is a weak hover signal on a translucent control. | 2026-08-20 | Tailwind | **Never hand-write a variant class as raw CSS.** `.dark\:hover\:bg-blue-600\/45 { ... !important }` is a *plain class selector* — no `:where(.dark, .dark *)`, no `:hover`. ## `@deprecated` is documentation, not removal

Asked to move the ECG strip out of `StatCard` into a child card, I added the child card, tagged `health`/`healthBpm` `@deprecated`, left the render branch in place, and wrote "moved" in the report. The user then saw the health examples still on the demo page — because the demo called the prop, and the prop still worked.

A JSDoc tag changes nothing at runtime and nothing in a demo. When the instruction is *move X out of Y*, "done" means Y can no longer do X: props gone, render branch gone, imports gone, and every call site migrated — including the ones in `// @ts-nocheck` files, which the compiler will not point at.

Verify it on the rendered output, not the prop table. A DOM probe counting `<canvas>` elements settled this in one command; reading the type definition would have shown a prop marked deprecated and told me nothing about what the page draws.

## A wrapper that renames its base's props is not inheritance

The Stat tiles all "extended `StatCardProps`" and none of them actually inherited it: each `Omit`ed nine or ten props and renamed what survived. Two consequences that only showed up when I tried to drive them all from one set of controls:

- `StatGraphTile` omitted `variant` and reused the name for the chart kind, so it was the one card in the family that could not be given a surface. A collision like that is invisible while each component has its own playground — every demo just shows the props that component happens to have.
- Tiles that extended *another wrapper* rather than the base inherited the renames as well, so the drift compounded a layer at a time.

The check that catches this is a `describe.each` over every member asserting the same base-prop contract against **rendered output**. Types cannot catch it: a wrapper that declares a prop and forgets to forward it type-checks perfectly.

## Shared demo controls are a test of the refactor, not a convenience

The requirement was "the playground options need to be the same as the base card". Two hand-maintained control lists satisfy that for exactly as long as nobody adds a prop. Extracting one hook that returns a `StatCardProps` object and spreading it onto every variant makes the requirement structural — and it only compiles *because* every variant really does take the base props, so the demo doubles as a check that the rebase is real.

## Read the attribute, not the pixel — twice, for two different reasons

Verifying the chart work headless produced two false alarms in one screenshot:

- **The bars were missing.** Not a bug: the mount animation had not completed under `--virtual-time-budget`. Re-rendering with `chartAnimation={false}` produced the rects. Anything that animates in needs its animation disabled before a headless screenshot means anything.
- **The axis labels looked orange.** Also not a bug — dumping the DOM showed `fill="#94a3b8"`, the correct slate-400. That is the SwiftShader channel-wrap artifact again, now three times.

Both would have cost real time to "fix". The DOM dump answered each in one command.

## Share the state, not necessarily the chrome

Three components wanted paging. The instinct was to make the two visible ones share a header component; the right split was to share only `usePager` — index, clamp, end conditions — and let each keep its own strip, because `PagedPanel`'s header carries a title, subtitle and divider that a metric card has no room for.

The test for where the seam goes: what would be a *bug* if the two disagreed? Two pagers that clamp differently is a bug. Two pagers that look different is a design decision. Share the first, not the second.

Extracting the clamp fixed a crash by construction — one copy read `data[index]` with no clamp and died when a reload returned a shorter list.

## An action control inside a clickable container needs stopPropagation

The pager arrows sit inside a card that is often `onClick`-able. Without `stopPropagation` on the arrow handler, pressing it pages *and* activates the card — two things happen, one of which the user did not ask for. Easy to miss because it only shows up in the combination, and neither component is wrong on its own.

## "Does not provide an export named 'default'" points at the importer, not the culprit

The error named an example file that plainly had a default export. The cause was a circular import two modules upstream: a component did `import { Panel } from "."`, and the barrel re-exports that same component. Vite HMR re-evaluates the barrel, an importer sees it half-initialised, and the missing binding is reported wherever the import statement happens to live.

Two things follow. First, when this error names a file whose exports are obviously fine, stop reading that file and go looking for a cycle through the barrel. Second, a component should never import its siblings via the package barrel — always the sibling module directly. It costs nothing and removes the cycle entirely.

Adding one new export to a barrel is enough to change evaluation order and turn a latent cycle into a reported bug, so this tends to surface right after an unrelated-looking change.


## Reproduce the failure mode before explaining it

Told that a module "does not provide an export named 'default'", I reasoned my way to a circular import through the barrel — a real latent problem, and not the cause. The user hit the same error again, which is what a confident wrong answer earns.

What settled it took two commands: connect to Vite's HMR socket and touch the file (Vite sends `full-reload`, not the `js-update` the error's `?t=` implied — so my story was already impossible), then truncate the file and request it (Vite serves a module with no exports — exactly the error).

The cause was my own tooling: rewriting a file with `cat > file` or a read-then-write script leaves it empty for a few milliseconds, and a running dev server's watcher can read it in that window. Write to a temp file and `mv` it into place, so the watcher only ever sees a complete file.

Two things I should have taken as signals much earlier. `tsc`, the production build and a fresh dev server all passed while the user kept seeing the error — that combination means the source is fine and the failure lives in a *stateful process*, not in a file. And the server recovers on its own while the browser does not, so the fix on the user's side is a reload, not a code change.

## A global string replace in a test file is not a scoped edit

Updating Picker's tests for a changed class shape, I used a plain `str.replace` — which replaces every occurrence. The same assertion text existed in `TagPicker`'s describe block in the same file, and TagPicker had not been migrated, so I silently rewrote a passing test for an untouched component into a failing one.

It cost a debugging detour because the failure looked like it was in the code I had just changed. The tell was the line number in the failure — line 63, not line 22 — which I should have read on the first pass instead of assuming the failure belonged to the test I had edited.

When editing tests, anchor the replacement on enough surrounding context to identify the one block, or pass a count.

## Four copies of the same tokens is the default outcome, not an accident

`Input`, `Select` and `SearchBar` each had a byte-for-byte copy of the same tone tokens, size scale and validation surfaces — including the same comments, which is how you can tell they were copied rather than independently derived. Asked to make a fourth component "look like the others", the tempting move is a fifth copy.

Promoting them to the theme and migrating two of the existing three **with no test changes** is what proves the tables were identical; if a migration needs a test edited, the copies had already drifted and that edit is the bug being found.

## Share what would be a bug if it disagreed; keep what is deliberately different

Migrating four fields onto one set of theme tokens, three were pure copies and one was not. `InputGroup` draws its edge with an `outline` instead of a `ring` — because its addons sit flush against the group's edges with opaque fills and paint straight over a ring, while outlines are painted after all descendants. That difference is a fix, recorded in a comment right above the tokens.

Folding it into the shared shape "for consistency" would have reintroduced the exact bug the comment describes. So the rule is not *share everything that looks similar*: share what would be a defect if two components disagreed, and leave alone what differs on purpose. `SearchBar` kept one genuinely local map for the same reason.

The migration test is whether existing tests need editing. Three components moved with **no test changes**, which proves the copies were identical. Had one needed an edit, that edit would have been a drift bug surfacing, not a chore.

## The same prop can correctly mean opposite things on two controls

`loading` on a picker should disable the trigger: there is nothing to choose until the list arrives, and opening onto an empty list tells the user "no results" when the truth is "not ready". `loading` on a search bar must *not* disable the input: the whole point is that you keep typing while the previous query resolves, and disabling would swallow keystrokes and fight the debounce.

Consistency across a component family is about the shared vocabulary — the prop name, the spinner, `aria-busy` — not about every component reacting identically. Ask what the control is for while it waits.

A related detail: don't dim a loading control. The dim belongs to `disabled`, where nothing else explains the inertness. On a loading control the spinner is the explanation, and fading it fades the one element carrying the message. `cursor-wait` says "not now" without hiding anything.

## An accent colour and a surface colour are not the same prop

Renaming SplitView's `color` to `tone` and feeding that one value to both the active-row accent *and* the new surface variant tinted the entire two-pane layout blue by default — silently repainting every existing usage.

The accent exists to stand out against the surface. Pointing both at one prop means the louder the accent, the louder the background it is trying to be distinguishable from, which is self-defeating as well as a behaviour change nobody asked for. Splitting them (`tone` for the accent, `surfaceTone` defaulting to `neutral`) keeps the default appearance identical to before and makes tinting opt-in.

The general shape: when adopting a shared system adds a *new* consumer of an existing prop, check whether the prop means the same thing to both consumers before reusing it.

## A fill replaces; a tint composites

SplitView differentiated its list pane with an opaque `bg-gray-50/80 dark:bg-gray-900/80`. That works exactly as long as the container behind it is also opaque. The moment the component gained glass variants, an opaque pane fill would have painted straight over the backdrop on that half.

`bg-black/[0.025] dark:bg-white/[0.025]` reads the same on a solid surface and composites correctly on a translucent one. When one region of a themeable surface needs to differ from its neighbour, tint it — do not fill it.

## An affordance at `opacity-0` is not an affordance

SplitView's expand caret only appeared on hover, so on a list where some rows have sub-items and some do not, there was no way to tell which was which without sweeping the mouse across every row. The feature existed and was effectively invisible.

Hover-reveal is right for a *secondary* action on a row that is obviously actionable. It is wrong when the control's presence is the only signal that a capability exists.

## Use a quoted heredoc when the text contains backticks

Appending a Markdown report with `<<PY` instead of `<<'PY'` let the shell run command substitution on every backtick in the document. It "succeeded" — the file was written, the script printed its success line — with every backticked identifier silently replaced by nothing, gutting both files.

Always `<<'EOF'` for content. And when a write is followed by a wall of `command not found`, that is the write being corrupted, not incidental noise: check the file before moving on.

## Check whether a component is even reachable before planning work on it

Asked to harden `SmartGridLayout`, the first useful thing I did was grep for its importers: there were none. It was absent from the barrel, had no tests and no docs page, and no consumer could import it at all.

That single fact reshaped the plan. Every rename became free — no call site can break when there are no call sites — so `editThemeColor` → `tone` needed no deprecation dance. And the "bugs" were not regressions to be careful around; they were the state the code had always been in, because nothing had ever exercised it.

Two greps (`grep -rn ComponentName src demo` and a look at the barrel) are worth doing before any plan for an unfamiliar component, and the answer changes how much caution the work deserves.

## `{ ...obj }` does not copy the arrays inside it

Three sites did `const next = { ...section }` and then wrote `next.rows[i] = …` or `next.items.push(…)`. The spread copies the object; `rows` and `items` are still the very same arrays React holds as `prev`.

It stays invisible until something reads the previous snapshot — which is exactly what persistence does. Adding autosave on top would have written corrupted layouts and made it look like a storage bug.

A deep-frozen input turns this class of error into a throw at the point it happens, which makes it a one-line test rather than an afternoon.

## An error boundary cannot catch a call made in its parent

Wrapping each dashboard tile in a boundary and writing `<Boundary>{def.render()}</Boundary>` does nothing. The `render()` call is evaluated while the **parent** builds its element tree, so the throw happens before the boundary has mounted, and a boundary only catches what its children throw during their own render.

The fix is to pass the function and let a child component call it: `<Boundary render={def.render} />`, where the boundary renders `<TileContent render={...} />` internally. Now the call happens inside the subtree the boundary is watching.

The same trap applies to anything that looks like "wrap this value" but is really "wrap this computation" — Suspense included.

## Fix the bug you wrote down, or say you didn't

I catalogued the fragile init-sync as bug §1.5 in the plan, then built four phases on top without fixing it, and only came back when the user said they were seeing issues. Worse, it turned out to be *more* severe than my own note: it did not just risk re-running, it discarded updates permanently when they arrived during an edit.

A plan entry is not a fix. If a phase ships without addressing something the plan listed, the progress note has to say so explicitly — otherwise the written plan reads as done and the bug becomes invisible to everyone, including the person who found it.

## A `display: none` element measures zero, including in the ref that just hid it

The section ghost was sized from a height measured in the section's own `ref` callback. Hiding the dragged section re-ran that callback, the element now measured `0`, and the stored height was overwritten on exactly the render where the ghost needed it — so the placeholder collapsed to a hairline, which is the thing it existed to replace.

Any measurement cached from a ref has to be guarded against the states where the element is not laid out. "Only record a value greater than zero" is usually enough, and it is cheaper than reasoning about callback ordering.

## jsdom drops `clientY` from synthetic drag events

There is no constructible `DragEvent` in jsdom, so Testing Library falls back to a plain `Event` and quietly discards pointer coordinates from the init object. Every `event.clientY < midpoint` comparison then reads `undefined < n` — always false.

The failure mode is worse than a crash: the handler still runs and always takes the same branch, so a test asserting that branch **passes for the wrong reason**. Two of mine did. Build the event with `createEvent`, `Object.defineProperty` the coordinate onto it, and stub `getBoundingClientRect` — jsdom reports zero-size boxes, so a midpoint is meaningless without it.

## Two drag types on one surface need two MIME types

Sections and items are both dragged around the same grid. Sharing `text/plain` meant every item drop zone lit up while dragging a section, because those handlers read the payload and look it up as an item id — a miss, but only after the highlight.

Giving each kind its own MIME type makes a drag visible only to the handlers that understand it, which is cheaper and more robust than every handler defensively checking whether the payload is the kind it wants.

## Synthetic drag events do not test drag-and-drop

Eleven passing tests, and the feature did nothing in a real browser. Dispatching `dragstart` / `dragover` / `drop` straight at a target verifies your handler logic and nothing else: there is no drag session, so nothing can cancel it, and nothing bubbles through the elements a real pointer would cross.

Three things were wrong that only a real drag reveals:

- **Hiding the drag source cancels the drag.** The browser needs it rendered while it takes the drag image. Defer the hide by a frame.
- **Unmounting the drag source cancels the drag.** A placeholder that removes the source from the list looks right in jsdom and dies in Chrome. Keep it mounted and `display: none`.
- **Sibling handlers that `stopPropagation()` swallow it.** Any nested drop target between the pointer and your listener will eat the event unless it knows to stand aside.

Also: `dragover` fires before React flushes `dragstart`'s state, so a handler gated on state misses the first frames and never calls `preventDefault()` — the browser refuses the drop for that window. Gate on a ref.

The test that would have caught it dispatches at a **descendant** of the target and lets the event bubble. Prove it by reverting the fix and watching it fail.

## An insertion placeholder cannot be driven by per-element hover

Dragging with a placeholder that occupies space is a feedback loop waiting to happen: inserting the placeholder shifts the layout, the target moves out from under the pointer, `dragleave` fires, the placeholder is removed, the layout shifts back, `dragover` fires. The user sees flicker.

The fix is to stop hit-testing live. Snapshot the item geometry once at `dragstart` and resolve the insertion point against that fixed snapshot for the whole drag — the placeholder then cannot influence its own position. Move the handlers to the container while you are there, so a drop landing on the placeholder still counts.

## `drop` fires before React re-renders, so drop handlers must read refs

`dragover` sets the pending target in state; `drop` arrives immediately after, closing over the render from *before* that update. On the first drop of a drag the handler reads `null` and silently does nothing — which presents as "it doesn't save".

Anything a drop handler needs must live in a ref that `dragover` writes synchronously. State is still worth keeping in parallel for rendering; the ref is what the handler trusts.

## A throw inside an event handler is silent

`event.dataTransfer.dropEffect = "move"` throws when `dataTransfer` is absent, as it is on synthetic events. Everything after that line simply never ran, with no test failure pointing at it — four tests failed on assertions about *ordering*, which sent me looking at the reorder logic instead of at a null property access three lines up.

When a handler "half works", check for a throw partway through before debugging the logic below it.

## A hand-rolled backdrop is a sign the control should be a primitive

An icon button was invisible in dark mode because its bespoke chip —
`bg-white/85 dark:bg-neutral-900/85` — only ever applied the light half. I could have chased why the dark variant did not win. The better move was to delete the chip: a solid kit `IconButton` already carries its own light and dark treatment, needs no backdrop, and reads as chrome over arbitrary content.

The general rule: writing a `dark:` pair by hand to make a *control* legible means the control is being built rather than used. Reach for the primitive and the theme handles both modes for free.

## Chrome inside a themeable component must follow its own theme

`SmartGridLayout` grew `variant` and `tone`, and every surface honoured them — except the editor's own buttons, which stayed `outline` / `ghost` / `slate`. The editing UI is the part the user looks at most while configuring, and it was the one part that ignored the configuration.

When adding a variant system, sweep the component's *own* controls too, not just the content surfaces. A map from the surface variant to the matching control variant makes it structural rather than a judgement call at each call site.

## A component that will be embedded should default to drawing nothing

`SmartGridLayout` defaulted to a `subtle` panel. Dropped into a page that already had its own container — worse, one with a background image — it drew a second grey slab on top, which is exactly what the user saw.

The default for anything meant to be embedded is *no surface*: no background, border, shadow, radius, and no padding either, because with no surface there is nothing to inset from and the host owns the spacing. A surface should be opt-in.

Two things follow from "I do not know what is behind me": controls take the glass treatment, which is designed for an unknown backdrop, and copy takes the higher-contrast translucent palette, because muted neutrals vanish over a photograph.

## Move destructive controls off the content, not just style them better

Every dashboard tile carried a delete button pinned to its top-right corner — which is exactly where the tile's own content (a StatCard's icon chip) sits. Because it overlapped arbitrary consumer content, it needed a backdrop to stay legible, and that hand-rolled backdrop is what later broke in dark mode.

The fix was not a better backdrop. It was to take the action off the content: a drop zone that appears only while something is being dragged, in a corner the component owns. That removes the overlap problem, the legibility problem and the always-armed-destructive-control problem in one move.

When a control needs a backdrop to survive the content underneath it, ask whether it belongs on that content at all.


## An arrow's caret must clear the corner radius

`Popover`'s arrow is a rotated square centred on the panel edge at the caret x. Left free, near the panel corners the diamond's centre lands inside the rounded region and the arrow visibly floats off the curve. The caret needs an inset of `cornerRadius + 8px` before it is clamped to the viewport — the 8px is half the arrow plus breathing room. The inset depends on the *configured* corner, so it comes from the same token the panel uses to round itself; hardcoding a "small" inset is a bug that only shows at `rounded-xl`.

## Completing a leave animation before asking for it tests nothing

The phase machine (`closed → entering → open → leaving → closed`) only adds the `--leave` class *after* a close intent lands. A test that dispatches a synthetic `animationend` for the leave phase without first triggering close finds the component still in `open` and the assertion fails on the class list — even though the component is correct. The helper must be two steps: initiate the close (click the trigger, or call the dismiss path), *then* complete the leave phase. A one-step "close it" helper hides the contract and turns every fixture into a mystery failure.

## Virtual time never fires `animationend`, and CDP ignores the reduced-motion flag

Extending the GlassBackground lesson: under `--virtual-time-budget`, Chrome fast-forwards `setTimeout` but does not complete CSS animations — so a component that *unmounts on `animationend`* (DatePicker, Popover) is permanently frozen in its `--enter` class in a virtual-time DOM dump, while a real browser settles it in 300ms. And `--force-prefers-reduced-motion` is not honoured when the browser is launched over CDP: `prefers-reduced-motion` still reports false. Verify animation-driven state machines in real time (Playwright `waitForTimeout`), and force reduced motion with `page.emulateMedia({ reducedMotion: "reduce" })` — the CDP media emulation is the only path that flips both the media query and the computed `animation-duration`.


## `getBoundingClientRect` lies while a transform is running

The Popover's first placement measurement ran in the same layout effect that started the enter animation — and `getBoundingClientRect` reports the *transformed* box. During the 300 ms enter the overlay is `scale(0.93)`, so the geometry saw a 7 %-smaller panel: grow-aligned boxes missed the trigger's edge by up to 21 px, and the error was invisible in jsdom (no compositor, no transforms) and in tests (mocked rects). What made it subtle: the `ResizeObserver` never corrected it, because it watches the *layout* box, which never changed — only the painted box did. Measure layout (`offsetWidth`/`offsetHeight`) for placement maths, and the bbox fallback only for environments without layout. The same bug was latent in the DatePicker's overlay, which shares the 0.93 enter scale.

## A rotated-square arrow leaks a "rotated rectangle" over translucent panels

The Popover arrow is a 16 px square rotated 45° (a diamond) centred on the panel edge, so half the diamond sits over the panel. For opaque variants the overlap is invisible (same fill). But a translucent fill (glass, liquid-glass, tonal) composites a second time over the panel, so the inner half of the diamond shows through as a faint rotated rectangle sitting on the surface. The fix is to clip the diamond to the *outer* half only: an `overflow:hidden` window sized to half the diamond's visual span (SIZE·√2/2 ≈ 11.31 px for a 16 px square) with its inner edge exactly on the panel edge, and the diamond centred on that edge. The V still meets the edge without a gap, but nothing is painted over the surface. The clip window's corner-centre is the edge point, so the square's centre lands (d−8) px from that corner on each axis.

Related: a borderless panel (subtle/tonal/simple have `ring-transparent`) gives its arrow `border-transparent` too — a transparent V on a near-white tint is an invisible arrow. The edge-chrome `border` token is consumed *only* by the arrow (the notch uses fill+backdrop), so the borderless variants now hand the arrow the tone's own `border` colour: the tip reads as outlined while its fill still matches the panel exactly, so the join carries no colour step.

## The pointing axis is never clamped — a detached indicator's gap is the offset

The shared tooltip/popover geometry (`resolveTooltipPlacement`) clamps only the *caret* (parallel) axis; the pointing axis is always exactly `trigger.edge + offset`, because clamping it would break the trigger↔box adjacency the arrow/dot depends on. Two consequences, both verified against the code rather than assumed: (1) a detached "thinking-bubble" dot floats in a gap that is *always* the configured offset, so gap-shrinking size logic is defensive dead code — a jsdom test that tried to engineer a squeezed gap with a trigger that fits on no side found the box clamp on the caret axis instead, and the gap stayed at the offset; (2) the offset must be part of the *fit* maths (`spaceOn >= needsOn`), or a bubble-mode panel flips too late, once the dot no longer fits. The dot wears the panel's edge chrome (full circular border + fill + backdrop) so it reads as a bead of the same surface, and — being detached — it needs no notch: the panel edge runs unbroken, the real simplicity win over the speech-bubble arrow.
